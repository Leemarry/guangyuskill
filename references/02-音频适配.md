# 音频比画面短：怎么拉长，什么时候不该拉

## 一、先算 r，再决定做法

`r = 目标时长 / 源时长`。

| r | 做法 | 理由 |
| --- | --- | --- |
| 0.80 – 1.00 | 裁掉尾部，做 0.8–1.5 秒淡出 | 别压。压缩比拉长更容易听出来 |
| 1.00 – 1.06 | 单次匀速，`atempo=r` 一段到底 | 6% 以内人耳分不出，不值得上复杂方案 |
| 1.06 – 1.40 | **连续变速 + 曲线摊平**（本文件重点） | 单次 atempo 也能出，但拿不到"越走越慢" |
| > 1.40 | **不要拉**：循环段落 / 补前奏尾奏 / 换曲 | 拉 40% 以上必然发虚发颤，且有明显的"拖" |

`r > 1.40` 时硬拉的后果是具体的：音头被拉长、瞬态变钝、鼓点变成"噗"，
而且片尾速度掉到 0.7 以下时，人耳会从"跟着走"切换成"等它走完"。
这种时候改结构比改参数有效 —— 找一段可以循环的 8 小节重复一次，比拉 40% 干净得多。

## 二、连续变速的三条硬规则

### 规则 1：总拉伸是固定预算

```
∫₀ᵀ ds / tempo(s) = 目标时长
```

这条式子决定了：**"前面慢一点"和"后面不那么拖"是同一件事的两面**。
片头倍率压下去，片尾倍率就必然抬起来 —— 不是两个独立的旋钮，是一个跷跷板。

实测对照（30.77s → 35s，`r = 1.137`）：

| 版本 | 片头 | 片尾 | 前后差 | 曲线形状 | 听感 |
| --- | --- | --- | --- | --- | --- |
| A | 0.955（慢 4.5%） | 0.740（慢 26%） | 21.5 点 | `p=2`，减速堆在后 1/3 | 前段近原速，后段明显拖 |
| B | 0.920（慢 8.0%） | 0.840（慢 16%） | 8.0 点 | `p=1`，线性 | 全程平缓下坡，收尾不拖 |

A 版实测拍长 0.597 → 0.741s（100.4 → 80.9 BPM），前后差 144ms；
B 版 0.624 → 0.677s（96.2 → 88.6 BPM），前后差 53ms。
B 版起点慢 4 BPM、终点快 7.7 BPM、中段几乎不动 —— 这就是"均衡"。

### 规则 2：片尾倍率不低于 0.84

慢 16% 是可听辨但不难受的上限。低于 0.84：

- 35 秒的片子里，观众在最后 8 秒会开始"等它走完"；
- 拍长超过 0.70s 后，连续的音符之间会出现空隙感，听成"一顿一顿"；
- 若同时有画面减速（人物步频下降），两者叠加会被放大。

曲线形状用线性（`p=1`）。`p=2` 会把减速全压在最后三分之一，
主观上更"拖"——因为人对**变化率**敏感，末尾突然降速比全程缓降更刺耳。

### 规则 3：速度变化必须连续

用 `librubberband` 的 `tempo` 参数（它带 runtime 标志 `T`），配 `asendcmd` 每 0.2 秒推一条命令：

```
atrim → asetpts → asendcmd(f=cmds.txt) → rubberband → afade → 增益
```

命令文件长这样（154 条覆盖 30.77 秒）：

```
0.0000 rubberband@rb tempo 0.919620;
0.2000 rubberband@rb tempo 0.919120;
...
```

**为什么不能分段 `atempo` 拼接**：`atempo` 是 WSOLA 实现，每次调用都重置内部相位与帧对齐。
14 段就是 14 次重置，段边界两侧的波形相位无关；`acrossfade` 只把**电平**接平了，
实际是把两个不同相位的信号相加 —— 那是梳状滤波，听感"空、薄、金属"。
而且分段必然是阶梯的：每段内匀速，段界跳一档。

## 三、两个时间轴，别搞混

`asendcmd` 的时间轴是**它收到的帧的 PTS**，也就是**原曲时间轴**，不是输出时间轴。

验证方法：发两条命令 `3s→0.8`、`5s→0.5`，理论输出 = `3/1 + 2/0.8 + ...`。
实测 15.482s 对得上理论 15.5s，说明命令按原曲位置生效。

所以曲线要按**原曲位置 s** 定义：

```
tempo(s) = a − (a − e) · (s/T)^p
```

- `a` = 片头倍率（用二分法解，使 ∫ds/tempo = 目标时长）
- `e` = 片尾倍率
- `p` = 形状指数（1 线性，2 集中后段）
- `T` = 原曲长度

脚本 `scripts/fit_audio.py` 会自动解 `a` 并实测校准（rubberband 的 latency 与帧对齐会带来几十毫秒偏差）。

## 四、实测校准（不要信理论值）

rubberband 有内部延迟和帧对齐，第一次渲出来的长度通常会差 30–80ms。
做法是渲一遍量一遍，用斜率修正：

```
dur = build(a)
if |dur - target| > 0.02:
    d_lo = build(a - 0.01)
    slope = (d_lo - dur) / (-0.01)
    a = a + (target - dur) / slope
```

一般 1–2 轮收敛到 ±1ms。示例片一次命中（a=0.91962，实测 35.0004s）。

## 五、淡入淡出与响度

- 淡入 0.35–0.45s（画面通常 0.7s 起幅，音频要晚于画面出现）
- 淡出 1.5–1.8s，结束在画面全黑前 0.1s 左右
- **不要用 `alimiter`**：动态小的素材（LRA < 3）被反复压会出现抽吸感。
  用纯线性增益（示例是 −2.5dB），目标是 −14 LUFS / 真峰 ≤ −1.5 dBTP
- `apad=whole_dur=目标` 会把还没淡完的音乐切断 —— 长度应由变速曲线控制，
  `apad` 只做最后 1ms 级修整

## 六、怎么验证"没有拖"

不要凭感觉。测拍长：滑窗自相关，窗 1.6s、步 0.5s，lag 搜索 0.42–0.90s。

```bash
python scripts/beatcheck.py bed.wav
```

通过判据：

- 起点与终点拍长差 **≤ 60ms**
- 相邻窗变化中位数 ≈ 0（有阶梯的话中位数会明显偏离 0）
- 拍长范围不能出现"半拍/双拍"跳变（那是检测失败，不是音频问题）

示例片 B 版：0.624 → 0.677s，差 53ms，逐窗单调平滑，通过。

## 七、混流时视频流必须不重编码

```bash
ffmpeg -i video.mp4 -i bed.wav \
  -map 0:v -map 1:a -c:v copy -af "volume=-2.5dB" \
  -c:a aac -b:a 192k -ar 48000 -ac 2 -t 35 -movflags +faststart \
  -y out.mp4
```

验证画面真的没动：比视频包的 md5。

```bash
ffmpeg -v error -i out.mp4 -map 0:v -c copy -f md5 -
```

无音轨版和配乐版必须完全一致（示例片三版同为 `e0ff73ad…`）。
不一致说明 `-c:v copy` 没生效，或者 filter 作用到了视频上。
