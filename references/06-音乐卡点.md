# 音乐卡点

> 这一篇解决的是"画面跟着音乐呼吸"。它和"连续过渡"不冲突：
> 连续过渡管的是**地貌怎么换**，卡点管的是**画面什么时候起伏**。
> 用错了会变成 MV 快切，那就违背了这套方法的前提。

## 一、先决定要不要卡

| 片子类型 | 卡点方式 |
| --- | --- |
| 一段旅程、慢推、不能有剪辑点 | **只卡"呼吸"**：亮度、粒子速度、海面波幅跟着低频起伏；不切镜 |
| 有明确段落（副歌进、鼓点落） | 卡"段落"：每 8–16 拍换一次地貌，靠接力过渡，不靠切 |
| 快切 MV | 不要用这套方法 |

判定标准很简单：**卡点触发的是"幅度变化"而不是"画面切换"**，就对了。
如果你发现自己在算"第 37 帧切到下一个镜头"，说明用错场景了。

## 二、为什么不按 BPM 均分

现成的 BPM 检测给出一个数（比如 92.5），然后按 `60/BPM` 均分网格 —— 这只在
**节拍器式**的音乐上成立。这类片子里的曲子常常：

- 本身是自由速度（钢琴、弦乐、人声吟唱）；
- 已经被拉伸过（`fit_audio.py` 拉过以后，同一拍的时刻全变了）；
- 有渐慢结尾。

按固定 BPM 均分，走到第二段就开始偏，第三段已经对不上了。

所以这里量的是**每一帧的能量**，不是"第几拍"。画面跟着曲线走，卡的是感觉，不是格子。

## 三、三个信号，各管一件事

`beatmap.py` 输出四条逐帧曲线（长度 = 总帧数，值域 0–1）：

| 字段 | 是什么 | 用来驱动 |
| --- | --- | --- |
| `bass` | 35–160 Hz 的 RMS | 冲击、推进、镜头微推、海面波幅 |
| `energy` | 全频段 RMS | 整体亮度、粒子密度、雾浓度 |
| `onset` | 频谱通量的局部峰 | 起手、抬手、鸟飞起这类"动作起始" |
| `peak` | `onset×0.6 + (bass,energy)×0.4` | 找"值得打点"的时刻（脚本内部用） |

用法原则：**一个信号只驱动一类东西**。三个信号同时驱动同一个属性，
看起来会"过度响应"，什么都在抖，反而没有节奏。

## 四、跑一遍

```bash
# 只分析，输出源时间轴
python scripts/beatmap.py song.mp3 --out beatmap.json

# 音频会被拉伸到 35s：卡点同时映射到拉伸后的时间轴
python scripts/beatmap.py song.mp3 --out beatmap.json --stretch-to 35 --end-tempo 0.84
```

屏幕会打出"最值得打点的 12 个时刻"，带 ASCII 强度条，不用开 json 就能判断：

```
时长 30.772s   帧率 30   检出 96 个起始点
----------------------------------------------------------
    0.87s  帧   26  0.91  #####################.
    2.13s  帧   64  0.78  ##################....
```

JSON 结构（`--stretch-to` 时多出 `*_out` 与 `stretch`）：

```jsonc
{
  "duration": 30.772, "fps": 30,
  "events":  [{"time": 0.87, "frame": 26, "strength": 0.91}, ...],
  "bass":    [0.02, 0.05, ...],       // 逐帧，长度 = 30.772×30
  "energy":  [...], "onset": [...],
  "stretch": {"target": 35, "end_tempo": 0.84, "a": 0.91961, "p": 1},
  "events_out": [{"src_time": 0.87, "time": 0.95, "frame": 28, ...}],
  "bass_out": [...]                   // 长度 = 35×30，直接喂 Remotion
}
```

## 五、最关键的一步：拉伸后必须重映射

音频被 `fit_audio.py` 拉长以后，**每一拍的位置都动了，而且不是等比例动的**
（曲线变速：片头 0.92、片尾 0.84，中间连续变化）。这时如果还拿源时间轴的
`bass` 去驱动画面，前 10 秒勉强对得上，后面就开始飘。

`--stretch-to` 做的就是这件事：用**同一条 tempo 曲线**把源时间映射到输出时间。

```
t_out(s) = ∫₀ˢ ds' / tempo(s')      tempo(s) = a + (e−a)(s/S)^p
```

注意这是**积分映射**，不是乘一个常数。同一个 `a` 由 `∫ds/tempo = 目标时长` 解出来，
所以 `beatmap.py` 与 `fit_audio.py` 算出来的 `a` 必须一模一样 —— 这是可校验的：

```bash
python scripts/beatmap.py song.mp3 --out bm.json --stretch-to 35   # 打出的 a
python scripts/fit_audio.py --src song.mp3 --dur 35 --dry-run      # 打出的 a
# 两者应相同（本项目实测都是 0.91961）
```

对不上就说明两条曲线不是同一条，画面会与音乐缓慢脱钩 —— 这种错误肉眼很难发现，
只能靠这个数字对齐。

## 六、在组件里怎么用

```tsx
import bm from './beatmap.json';

const beat = bm.bass_out[frame] ?? 0;         // 逐帧取值，不要 t*系数
const push = 1 + 0.02 * beat;                  // 幅度要小：2% 就够，5% 就俗
const waveAmp = 0.6 + 0.4 * beat;
```

三条写法纪律：

1. **逐帧查表，不要 `Math.sin(t*…)` 造节拍** —— 那是"假卡点"，和音乐无关。
2. **幅度要小**。视觉上的 2–3% 已经很明显；超过 5% 会变成"抖"。
3. **同一帧只取一个信号**。`bass` 给冲击、`energy` 给亮度，不要一个属性叠两层。

## 七、踩过的坑

| 症状 | 根因 | 解法 |
| --- | --- | --- |
| 通量曲线的峰值全挤在一起、看不出节奏 | `np.diff` 做在了频率轴（`axis=1`）上，等于"频谱斜率"，与时间无关 | 沿**时间**轴做差分：`np.diff(..., axis=0)`。`mag` 是 (时间, 频率) |
| 数组长度比帧数少 1，画面整体错一帧 | `diff` 后长度变 `n−1`，补零时写成了 `np.r_[0, flux]` | `np.r_[0.0, flux[:-1]]` |
| 拉伸后卡点越到后面越偏 | 直接用了源时间轴的数组 | `--stretch-to`，走 `t_out` 积分映射 |
| 小鼓点全被检出，一帧一个 | 阈值 `floor` 太低、`min_gap` 太小 | `floor=0.20`、`min_gap=0.22s`（默认值就是调过的） |
| 每个镜头都跟着低频抖 | 幅度过大 + 多信号叠加 | 幅度 ≤3%，一个信号只驱动一类属性 |
